## 阅读约定

以下是**模拟输入和对应程序行为**。除特别标注的实际日志回放外，日期与上游动作均为假设，
不代表 Tibo 或任何服务商公布了固定重置时间。

| 项目 | 示例约定 |
|---|---|
| 时区 | 机器本地时间，示例按北京时间 UTC+8 |
| `primary` | 五小时窗口，`windowDurationMins=300` |
| `secondary` | 七天窗口，`windowDurationMins=10080` |
| 百分比 | **已用比例**；已用 90% 表示剩余约 10% |
| `resetsAt` | 接口返回的到期时间；表中换算为可读日期时间 |
| 轮询周期 | `poll.intervalMinutes=60` |
| 周期时间点 | 假设已安装为每小时 `:56`，如 08:56、09:56、10:56 |
| 每日上限 | `maxPerDay=6` |
| 最小间隔 | `minimumGapMinutes=300`，即五小时 |
| 立即触发 | `anchorOnApply=false`，除非场景另行开启 |
| 基础条件 | 当前机器可以执行、读取成功、无退避、无额度限制标记、模型配置有效、事件未被占用 |

**表中的“调用一次”表示允许进入锚定流程。** 后续模型校验、事件占用检查或实际执行仍可能失败。
调用后的用量与到期时间由服务端决定；例如“随后读到 1%”只是示例，不表示一次调用固定消耗 1%。

### 三种时间要分开看

1. **上游发生变化的时间**：例如 21:10 使用重置卡，或上游统一重置。
2. **程序读取到变化的时间**：例如下一次轮询 21:56。
3. **程序决定调用的时间**：可能是 21:56，也可能要等确认空闲、退出退避或满足间隔。

到期检查任务是 Windows 后台计划任务，**不弹窗、不播放铃声**。
它只启动检查；到点不代表一定调用模型。系统调度、锁等待和请求耗时会带来延迟。

## 1．不开启／开启 AutoAnchor，不同组合如何运行

### 1.1 不开启实验功能

```json
{
  "mode": "MonitorOnly",
  "codex": {
    "autoAnchor": {
      "enabled": false
    }
  }
}
```

| 时间 | 读取到的状态或用户动作 | 程序行为 |
|---|---|---|
| 08:56 | primary 已用 30%，到期 12:00；secondary 已用 90%，到期 09-18 18:20 | 更新状态和日志，0 次模型调用 |
| 09:10 | 用户在工具之外手动重置并继续使用 | 程序此刻没有运行，不会立即知道 |
| 09:56 | secondary 已用 3%，到期变成 09-22 09:12 | 记录到期前恢复，更新周额度状态，仍为 0 次模型调用 |
| 12:56 | 观察到五小时窗口变化 | 记录变化，仍不锚定 |

**关闭 AutoAnchor 不等于关闭程序。** 周期轮询、状态记录，以及已配置的多机协调／历史同步仍可工作。
通过安装或应用配置关闭实验功能后，不再维护实验功能的每日触发器和到期检查任务。

### 1.2 开启后的配置速查

下表的 `enabled` 指 `codex.autoAnchor.enabled`；各行均假设配置已应用。

| `mode` / `enabled` | `schedule` | `anchorOnExpiry` | 实际效果 |
|---|---|---|---|
| `MonitorOnly` / `false` | 任意残留值 | 任意残留值 | 只监控，不自动调用 |
| `AutoAnchor` / `false` | 任意 | 任意 | 实验功能仍未启用，只监控 |
| `MonitorOnly` / `true` | 任意 | 任意 | 配置组合无效，校验拒绝 |
| `AutoAnchor` / `true` | `[]` | `[]` | 没有自动触发来源；`anchorOnApply=false` 时只监控 |
| `AutoAnchor` / `true` | `["09:00"]` | `[]` | 每天 09:00 检查是否需要启动五小时窗口 |
| `AutoAnchor` / `true` | `[]` | `["secondary"]` | 只对周窗口的空档做补充，不负责每天 09:00 |
| `AutoAnchor` / `true` | `[]` | `["primary"]` | 对五小时窗口的空档做补充，不固定对齐 09:00 |
| `AutoAnchor` / `true` | `["09:00"]` | `["secondary"]` | 每日定时与周窗口到期独立判断，可合并 |
| `AutoAnchor` / `true` | `["09:00"]` | `["primary","secondary"]` | 三类条件都可能成为触发原因，仍执行去重和次数限制 |

下面各场景的配置表只列 `codex.autoAnchor` 下需要关注的字段。
它们是对现有 `config.json` 的修改项，不是要求删除其他配置。

## 2．`schedule=["09:00"]`：提前用过与没有提前用

本节配置：`enabled=true`、`schedule=["09:00"]`、`anchorOnExpiry=[]`。

### 2.1 07:40 提前使用，09:00 时五小时窗口仍在运行

| 时间 | 状态 | 程序行为 |
|---|---|---|
| 07:40 | 用户开始使用；假设 primary 到期时间为 12:40 | 上游窗口已开始 |
| 08:56 | primary 已用 6%，到期 12:40 | 普通轮询，09:00 尚未到 |
| 09:00 | primary 已用 7%，到期仍为 12:40 | **不调用**；09:00 槽位标为已处理 |
| 12:40 | 五小时窗口到期 | 本配置没有 primary 到期触发器，不安排补充调用 |
| 12:56 | 读到窗口已到期／空闲 | 不补打今天的 09:00 |

“槽位已处理”表示今天这个时间点的机会已消费，即使没有调用模型也不会稍后重试该槽位。

### 2.2 从未提前使用，08:56 和 09:00 都读到滚动预测

| 读取时间 | primary 已用 | 返回的到期时间 | 判定 |
|---|---:|---|---|
| 08:56:00 | 0% | 13:55:56 | 接近当前时间 +5 小时，先作为空闲候选 |
| 09:00:00 | 0% | 13:59:56 | 随查询后移 4 分钟，确认空闲 |
| 09:00 附近 | — | — | **允许一次 schedule 锚定** |
| 调用后读取 | 假设 1% | 假设固定到期时间为 14:00:05 | 保存实际返回的状态；同一槽位不再调用 |

单独配置 schedule 不会让程序在 14:00 再补一次。下一次每日定时是次日 09:00。

### 2.3 提前用过，但窗口在 09:00 之前已经到期

| 时间 | 状态 | 程序行为 |
|---|---|---|
| 03:15 | 用户使用；假设五小时窗口到期 08:15 | 产生一个已运行的窗口 |
| 09:00 | 当前 primary 到期时间仍是 08:15，且读取成功、没有限制标记 | **允许一次 schedule 锚定** |

如果 09:00 返回的是“0% + 新的滚动预测”，则先按上一小节的连续观测规则确认。

**结论：提前用过不代表一定跳过。关键是 09:00 检查时，五小时窗口是否仍在运行。**

### 2.4 周额度已经在使用，五小时窗口却空闲

09:00 读到 secondary 已用 45%、到期 09-18 18:20；primary 已确认空闲。

**允许 schedule 锚定。** 每日定时检查的是 primary 是否正在运行，周额度处于运行期不会单独阻止它。
如果服务端同时返回额度限制标记，则由公共校验阻止调用，见[第 10 节](#s10)。

### 2.5 一天设置多个时间点，并不保证每个时间点都调用

配置改为 `schedule=["09:00","13:00","15:00"]`，没有 expiry 触发器。

| 时间 | 假设读取结果 | 程序行为 |
|---|---|---|
| 09:00 | primary 已过期 | 调用一次；假设之后窗口固定到 14:00 |
| 13:00 | primary 已用 4%，仍到期于 14:00 | 跳过并消费 13:00 槽位 |
| 15:00 | primary 已过期／已确认空闲 | 15:00 是独立槽位，可再调用一次 |

若 14:30 你已经使用并启动新窗口，15:00 也会跳过。schedule 提供检查机会，不强制重开仍在运行的窗口。

## 3．单次 0%、任务迟到、关机和补跑期限

### 3.1 09:00 是第一次看到 0%，没有足够历史

仍使用 `schedule=["09:00"]`，周期轮询为每小时 `:56`。

| 时间 | 读取结果 | 程序行为 |
|---|---|---|
| 09:00 | primary 0%，到期 13:59:56，没有可用于确认的前一快照 | 不调用，槽位暂不消费，原因是等待空闲确认 |
| 09:56 | 仍为 0%，到期后移至 14:55:56 | 确认空闲，迟到 56 分钟仍在 60 分钟期限内，允许调用 |

反例：09:56 到期时间仍固定为 13:59:56。此时不能认为是滚动空闲预测，按运行窗口处理，跳过并消费槽位。

这能避免把“刚开始使用，但百分比四舍五入仍显示 0%”立即当成空闲。

### 3.2 补跑期限是一个轮询周期，不是整天

前提：09:00 槽位未处理，primary 已过期或已确认空闲，其他校验通过。

| 完成读取并做决策的时间 | 距离 09:00 | `intervalMinutes=60` 时的结果 |
|---|---:|---|
| 09:40:00 | 40 分钟 | 可以补跑 |
| 10:00:00 | 恰好 60 分钟 | 按当前比较条件仍可补跑 |
| 10:00:01 | 60 分钟 1 秒 | 超时，消费槽位，不补跑 |
| 11:00:00 | 120 分钟 | 不补跑 |

> 比较使用的是**读取后做判断的时间**。10:00 才开始启动，读取耗时几秒，也可能已经超时。
> 若轮询间隔改为 15 分钟，补跑期限随之变成 09:15，而不是仍到 10:00。

### 3.3 电脑关机、睡眠或未登录

| 场景 | 示例 | 行为 |
|---|---|---|
| 09:00 关机，09:40 登录后补执行 | 决策在 09:40:05，primary 已过期 | 可在期限内补跑 |
| 09:00 关机，11:00 才登录 | 决策已超过 60 分钟 | 消费迟到槽位，不调用 |
| 睡眠，`wakeToRun=false` | 09:00 未唤醒 | 等系统恢复可运行后再检查，仍受补跑期限限制 |
| 睡眠，`wakeToRun=true` | 请求系统在触发时间唤醒 | 是否成功由硬件和电源策略决定；成功后仍重新读取额度 |
| 用户未登录 | 任务使用 Interactive 登录类型 | 不能保证无人登录时运行；关机也不能靠该选项开机 |

`StartWhenAvailable=true` 提供恢复运行后的补执行机会，不保证错过的每个周期都逐一补跑。

### 3.4 跨过午夜，不回补昨天的每日槽位

配置 `schedule=["23:30"]`，周期 60 分钟；电脑在 23:20 关机，次日 00:10 恢复。

虽然只比昨天的 23:30 晚了 40 分钟，当前实现只枚举**今天**的每日槽位，因此不会回补昨天的 23:30。
下一次该每日槽位是今天 23:30。若另有 expiry 配置，到期条件仍可独立判断。

## 4．只配置 secondary，七天额度没有提前重置

本节配置：`schedule=[]`、`anchorOnExpiry=["secondary"]`。
假设已知周额度到期时间为 **09-18 18:20:00**，旧周窗口的已用比例为 40%。

### 4.1 正常到期，接口明确返回到期状态或空值

| 时间 | 读取结果／任务状态 | 程序行为 |
|---|---|---|
| 09-18 17:56 | secondary 已用 40%，到期 18:20 | 设置到期检查任务为 18:21 |
| 18:20 | 已知周窗口到期 | 不假设系统此秒一定执行程序 |
| 18:21 附近 | 任务启动，读取后 secondary 的 `resetsAt` 已过期或明确为 `null` | 允许一次 expiry 锚定 |
| 调用后 | 假设读到新的真实周到期时间 09-25 18:21:05，已用 1% | 更新状态，将下一次到期检查指向 09-25 18:22:05 |

这里“到期 +1 分钟”是**检查启动目标**；真实调用还要加调度和读取耗时。

### 4.2 正常到期后，接口返回的是滚动空闲预测

| 读取时间 | secondary 已用 | 返回的到期时间 | 行为 |
|---|---:|---|---|
| 09-18 18:21:00 | 0% | 09-25 18:20:56 | 第一个空闲候选，不立即调用 |
| 09-18 18:56:00 | 0% | 09-25 18:55:56 | 连续后移，确认空闲，允许 expiry 锚定 |

所以这个场景可能在 **18:56 附近**才调用，而非必然在 18:21 调用。
如果当时还有最小间隔、每日上限或退避，时间还会继续后移。

### 4.3 到期后你先使用了新额度

18:20:20 你开始使用。18:21 程序读到 secondary 已用 1%，新到期时间为 09-25 18:20:20。

**不调用。** 新周窗口已经运行，程序更新到期检查为 09-25 18:21:20。

### 4.4 同一空闲期持续很久

假设一次 expiry 尝试已处理，但后续读取仍显示空闲：

- 18:56、19:56、次日 00:56 的预测时间持续后移，不生成新的到期事件 ID。
- 即使超过 300 分钟最小间隔，或者工具重启，也不会仅因同一预测后移再调用。
- 一旦观察到真实的新窗口，才更新到期点，为新周期建立后续触发依据。

<a id="s05"></a>
## 5．只配置 secondary，七天额度提前重置

仍为 `schedule=[]`、`anchorOnExpiry=["secondary"]`。
假设旧周额度到期时间为 **09-18 18:20**，你在 **09-15 21:10** 手动使用重置卡。

### 5.1 提前重置后，你又使用了一点

| 时间 | 用户操作／读取快照 | 程序行为 |
|---|---|---|
| 20:56 | secondary 已用 90%，到期 09-18 18:20 | 旧到期检查仍指向 09-18 18:21 |
| 21:10 | 用户重置 | 此时没有触发器启动，程序尚不知道 |
| 21:12 | 用户继续使用，新周窗口开始 | 上游产生新的真实到期时间 |
| 21:56 | secondary 已用 10%，新到期时间为 09-22 21:12 | 记录 `QUOTA_RECOVERED_EARLY`，不调用模型 |
| 同一轮结束 | — | 到期检查更新为 09-22 21:13，不再按旧 09-18 时间判断 |
| 22:56 | secondary 已用 11%，到期不变 | 普通用量变化，不重复记录提前恢复 |

**提前恢复事件只说明观测到的变化，不会单独触发调用。**
`reason=unknown`；无法从额度快照区分手动重置卡、上游统一重置或其他原因。

### 5.2 提前重置后没有使用，返回滚动空闲预测

| 读取时间 | secondary 快照 | 行为 |
|---|---|---|
| 21:56:00 | 0%，到期为 09-22 21:55:56 | 记录从 90% 降到 0% 的提前恢复；空闲仍待确认，不调用 |
| 22:56:00 | 0%，到期后移至 09-22 22:55:56 | 确认空闲；允许一次 expiry 锚定 |

**不会死等旧的 09-18 18:20。** 当前实现的 `anchorOnExpiry` 也处理选定窗口的已确认空闲，
并非只在墙上时间超过旧截止日期后才行动。

如果你在 22:10 已经使用新额度，22:56 就改走 5.1 的“已运行，不调用”分支。

### 5.3 提前重置后，返回空值或窗口消失

前提是整次读取成功、响应结构可识别；超时或未知结构不等于窗口消失。

| 下一次 21:56 的响应 | 本地历史 | 当前实现 |
|---|---|---|
| secondary 存在，`resetsAt=null` | 可有可无 | 按未运行处理，允许 expiry；其他校验仍有效 |
| secondary 完全消失 | 曾跟踪过 secondary | 使用保留的事件标识，允许 expiry，**即使旧到期时间仍在未来** |
| secondary 完全消失 | 从未跟踪过 secondary | 没有依据，不凭空创建该窗口的 expiry |
| secondary 为 0%，但到期固定在 09-17 12:00 | 到期在未来，且不是接近当前 +7 天的滚动预测 | 按运行窗口处理，不调用 |

单凭“窗口消失”不会记录 `QUOTA_RECOVERED_EARLY`；它缺少可比较的当前用量／到期值。
状态机会产生 `WINDOW_DISAPPEARED`，随后锚定判断独立进行。

### 5.4 已用比例恢复，但到期时间没变

20:56：90%，到期 09-18 18:20。21:56：10%，到期仍是 09-18 18:20。

记录提前恢复；当前窗口仍在运行，所以不调用，到期检查仍指向 09-18 18:21。
相反，真实到期时间改变但已用比例仍为 90%，也可记录“到期前窗口重置”，原因保持未知。

## 6．类似 Tibo 那边在某个时间统一重置

**这里只假设上游在 09-15 21:10 改变了账号额度，不判断 Tibo 是否、何时或如何执行该操作。**
工具没有订阅上游公告，也没有内置“21:10 统一重置”的日历。

### 6.1 通常多久会发现

周期轮询为 20:56、21:56、22:56；当前没有更早的每日定时或到期检查。

| 时间 | 发生的事 | 工具何时知道 |
|---|---|---|
| 21:10 | 上游统一重置 | 此刻通常不知道 |
| 21:56 附近 | 下一次成功轮询 | 约 46 分钟后观察到变化 |

若 21:20 恰好另有已配置的每日定时或到期检查，并成功读到新额度，则可提前到 21:20 附近发现。
健康运行且没有其他触发器时，检测延迟通常在一个轮询周期内，再加调度和请求耗时；
关机、未登录、断网、退避、PASSIVE 状态会打破这个时间范围。

### 6.2 同一次上游重置，不同配置的结果

假设 21:56 读到 primary 和 secondary 都是 0% 的首次滚动预测，22:56 连续后移确认空闲。

| 配置 | 21:56 附近 | 22:56 附近 |
|---|---|---|
| MonitorOnly | 记录可确认的变化 | 继续记录，不调用 |
| AutoAnchor，但两个触发器都为空 | 记录变化 | 不调用 |
| 仅 `schedule=["09:00"]` | 今天的 09:00 已处理或已超时，不立即调用 | 不调用；次日 09:00 再按当时状态判断 |
| 仅 `anchorOnExpiry=["secondary"]` | 等待周窗口空闲确认 | 允许一次 expiry |
| `schedule=["09:00"]` + secondary | 当天 09:00 不补跑，周窗口等待确认 | 由 expiry 触发一次 |
| primary + secondary | 两个窗口分别等待确认 | 两个到期事件合并为一次物理调用 |

若 21:56 已读到新窗口有实际使用，则相应窗口不走空闲触发。
若返回明确空值／已跟踪窗口消失，则按 5.3 判断，可能在 21:56 就允许调用。

### 6.3 上游重置与 09:00 靠得很近

配置仅为 `schedule=["09:00"]`：

| 时序 | 09:00 行为 | 后续 |
|---|---|---|
| 08:50 重置，09:00 首次读到 primary 的滚动 0% | 待确认，保留槽位 | 09:56 确认空闲且仍在期限内，可补跑 |
| 08:50 重置，08:52 你已开始使用 | 读到 primary 已运行，消费槽位 | 不再补打今天的 09:00 |
| 09:00 读到旧窗口仍运行，09:01 上游才重置 | 09:00 槽位已消费 | 后续发现重置也不会重新打开这个槽位 |

如果同时配置 secondary，到期／空闲触发仍独立判断；“09:00 已消费”不会禁用整天的 expiry。

<a id="s07"></a>
## 7．只设 primary，或同时设两个窗口

### 7.1 只补五小时窗口

配置：`schedule=[]`、`anchorOnExpiry=["primary"]`。

| 时间 | primary | secondary | 程序行为 |
|---|---|---|---|
| 08:56 | 已用 5%，到期 13:20 | 已用 30%，到期 09-18 18:20 | 设置到期检查为 13:21 |
| 13:21 | 已过期／空值，且无额度限制 | 仍在运行 | 允许一次 primary expiry |
| 13:21 | 改为首个滚动 0% 候选 | 仍在运行 | 等待连续确认，可能在 13:56 才允许调用 |

只设 secondary 时，表中的 primary 到期不会成为触发理由。
同样，只设 primary 时，secondary 的变化可被记录，但不会作为周窗口 expiry 触发。

### 7.2 primary 与 secondary 同时未运行

配置：`anchorOnExpiry=["primary","secondary"]`，两者的旧到期点都已到达，且本轮读到明确到期状态。

- 产生两个 expiry 事件 ID，分别检查是否已占用。
- 两个事件都获准时，合并为**一次物理模型调用**，每日尝试次数增加 1。
- 一个事件已有记录、另一个尚未处理时，只对尚可执行的事件处理，不重做已占用事件。

<a id="s08"></a>
## 8．`schedule=["09:00"]` 与 secondary 同时开启

### 8.1 两个原因在同一轮都满足

09:00 读到：primary 到期时间为 08:59，secondary 的旧到期时间也已过去，均无限制标记。

| 项目 | 结果 |
|---|---|
| 每日定时 | 今日 09:00 槽位可执行 |
| 周额度 | secondary expiry 可执行 |
| 合并后的原因 | `schedule+expiry` |
| 模型调用 | 两个事件都获准时，共 1 次 |
| 每日尝试次数 | 例如从 2 增加到 3，不是增加到 4 |

09:01 的到期检查即使又启动一轮，也要重新读取并检查事件占用，不会重复执行已经处理的原因。

### 8.2 你提前使用了五小时额度，但周窗口需要补充

09:00 读到：primary 已用 5%、到期 12:40；secondary 明确未运行。

1. schedule 因 primary 仍在运行而跳过，并消费 09:00 槽位。
2. secondary expiry 仍可成立。
3. 本轮最终可能以 `expiry` 原因调用一次，且要满足 300 分钟最小间隔。

**因此，“提前使用过，所以今天 09:00 肯定不调用”只适用于没有其他触发原因的情形。**

<a id="s09"></a>
## 9．最小间隔、每日上限与立即触发

### 9.1 满足最小间隔，不会额外创建一个立即执行的计时器

假设上一次**工具实际尝试调用**在 09:00:05，`minimumGapMinutes=300`。
仅配置 secondary expiry，周窗口在 12:00 到期，之后一直未运行。

| 决策时间 | 距上次尝试 | 行为 |
|---|---:|---|
| 12:01 | 约 181 分钟 | 不足 300，跳过 |
| 13:56 | 约 296 分钟 | 仍不足，跳过 |
| 14:00:05 | 恰好达到 300 分钟 | 仅达到资格，不保证此时有任务启动 |
| 14:56 | 约 356 分钟 | 下一轮若仍符合条件，则允许调用 |

最小间隔依据工具记录的 `lastAttemptAt`，不是你本人最后使用 Codex 的时间。
你在 13:00 手动使用不会直接改这个字段，但可能让窗口恢复运行，从而使 expiry 不再成立。

### 9.2 schedule 与立即触发可以越过最小间隔，不能越过每日上限

上次工具调用在 08:30，09:00 primary 已明确到期：

| 条件 | 结果 |
|---|---|
| 只有 expiry，间隔 30 分钟 | 跳过，最小间隔未满足 |
| 09:00 schedule 符合条件 | 可以调用，不受 300 分钟间隔限制 |
| 显式 `anchorOnApply` 请求，其他条件允许 | 可以调用，不受间隔限制 |
| 今天尝试次数已经达到 6 | 三种入口都拒绝，不会因 schedule 或 force 绕过上限 |

每日计数在进入新的机器本地日期后重新计算。计数归零不会清除已经占用的旧事件，也不等于午夜自动调用。

### 9.3 `anchorOnApply=true`

前提：`mode=AutoAnchor` 且 `enabled=true`。

| 时间 | 操作 | 行为 |
|---|---|---|
| 08:30 | 运行 `apply-config.cmd`，今天尚未做过 apply 强制尝试 | 请求立即调用，即使两个窗口都在运行，也不等到 09:00 |
| 08:35 | 再次运行 `apply-config.cmd` | 今天已经实际尝试过 apply 强制调用，不重复 |
| 次日 08:30 | 再次应用配置 | 当天可再请求一次，仍受所有其他校验约束 |

设置这个字段后，安装或升级时运行 `install.cmd` 也可能请求立即调用。
不需要这种行为时，保持默认 `anchorOnApply=false`。

### 9.4 失败是否计次数

- 模型执行进程已启动，随后报错、超时或验证读取失败：通常仍计为一次尝试，不自动重试同一事件。
- 能确认进程根本没有启动：撤销本次次数预留，但该事件仍被标记失败／已处理，不保证可重试。
- 模型配置在占用事件前就被判定无效：没有执行，不增加次数；修正后仍受槽位补跑期限约束。

<a id="s10"></a>
## 10．网络、额度限制、重置卡与退避

### 10.1 常见失败之后，几点才再次检查

以下时间以本轮错误在 09:00:05 被记录为例，周期轮询仍为每小时 `:56`，且没有其他触发器。

| 读取结果 | 程序设置 | 后续时间示例 |
|---|---|---|
| 网络错误／超时／EOF | 本机退避 10 分钟 | 09:10:05 之后具备再次读取资格；实际下一轮可能是 09:56 |
| 429，分类为 `RATE_LIMITED` | 本机退避 60 分钟；开启协调时发布集群退避 | 09:56 仍跳过；下一轮 10:56 才重读 |
| 认证错误 | 本机退避 120 分钟；开启协调时发布集群退避 | 09:56、10:56 跳过；11:56 再检查 |
| 未知响应结构 | 保留旧快照并标记 stale，禁止锚定 | 后续正常触发时再读，不能把解析失败当成空闲 |
| 成功读取，但带 `rateLimitReachedType` | 限制标记阻止本轮锚定 | 不等同于读取失败的 429，不因此自动创建同样的 60 分钟退避 |

退避到期本身不会新增一个到点启动任务；必须等下一个实际触发时刻。
仅看到已用 100%，也不能把整次读取等同于 429；要看服务端限制字段和错误分类。

### 10.2 已经进入退避，此时使用重置卡

| 时间 | 动作／状态 | 程序行为 |
|---|---|---|
| 09:00:05 | 额度读取返回 429 | 设置退避到 10:00:05 |
| 09:10 | 你手动重置并恢复额度 | 不会自动清除工具已有的退避记录 |
| 09:56 | 周期任务启动 | 仍在退避，不读取新额度，不锚定 |
| 10:56 | 再次轮询，退避已结束 | 成功读取后才采用重置后的状态 |

如果此时只有 `schedule=["09:00"]`，10:56 已超过补跑期限，今天的 09:00 不会补打。
如果同时有 secondary expiry，它仍按新快照、空闲确认和次数限制独立判断。

### 10.3 模型调用报错，不能只看额度是否仍空闲

09:00 的调用进程已经启动，但响应超时。即使 09:56 仍读到 primary 为 0%，也不会自动重试同一个 09:00 事件。
原因是无法确认服务端是否已经接受过第一次请求，持久事件记录会阻止重复执行。

<a id="s11"></a>
## 11．多机、任务并发与进程崩溃

### 11.1 家里和公司两台电脑都配置了 09:00

开启多机协调，A 持有有效租约，B 为 PASSIVE：

| 时间 | A | B |
|---|---|---|
| 09:00 | 读取额度，按条件决定是否锚定 | 发现 A 的有效租约，不查询额度、不锚定 |
| 10:00 | 假设 A 的租约名义到期，且 A 已离线 | 尚需考虑配置的 5 分钟宽限 |
| 10:06 | A 没有续租 | 若 B 此时被触发、允许接管且竞争成功，可成为 Leader |

10:06 接管时不会补打已经超过 60 分钟期限的 09:00；到期触发仍可独立成立。
B 若要到 10:56 才运行，也不会在 10:06 自动醒来抢租约。

> 两台电脑都关闭协调时，会各自作为本机 Leader，不能保证跨电脑只有一次调用。
> 协调已开启但远程不可达时，不通过自动降级为无锁模式来调用模型。

### 11.2 周期轮询与到期检查撞在一起

- 08:56:00 周期任务持有运行锁；08:56:10 到期检查启动。
- 到期检查最多等待锁 60 秒。若 08:56:20 得到锁，重新读取并重新判断，不沿用等待前的旧结论。
- 等待超时则退出，由后续触发继续检查。
- 同一计划任务自身同时触发时，`IgnoreNew` 也可能忽略新实例，因此不要把“触发器到点”理解为必有一轮完整执行。

### 11.3 调用前后崩溃

事件在调用前先取得持久占用记录。若进程在占用后崩溃，同一事件不会因为工具重启或换 Leader 而自动重试。
普通定时到期也不会仅凭占用记录中的超时时间就重新尝试；需要结合日志人工调查。

同一空闲期保持原事件 ID；真实的新窗口和新的每日槽位可以产生各自的新事件。

## 12．应用配置、升级、只读状态与日志解释

### 12.1 应用配置会改变周期起点

假设原周期为每小时 `:56`，你在 14:20:00 运行 `apply-config.cmd`：

| 项目 | 变化 |
|---|---|
| 周期轮询 | 重注册后约 14:21 首次触发，随后 15:21、16:21…… |
| `schedule=["09:00"]` | 仍是本地每日 09:00，不跟着变成 09:21 |
| 今天已处理的 09:00 | 不会因 Apply 自动清空或补打 |
| `anchorOnApply=false` | Apply 不请求立即模型调用 |
| `anchorOnApply=true` | 可能请求当天的一次立即调用，见 9.3 |

只改 `config.json` 而不 Apply，旧的 Windows 触发器定义可能尚未同步；请按 README 的应用流程操作。

### 12.2 升级之后，历史槽位与事件继续保留

升级保留 `config.json`、`runtime/`、`history/` 和机器身份。
例如今天 09:00 在旧版已被误标为处理完成，修复后不会自动删除这个历史标记来补打。
后续新槽位使用修复后的判断；新的空闲观测信息会随正常成功读取建立。

### 12.3 `status.cmd` 与 `status.cmd -Live`

| 操作 | 会发生什么 | 不会发生什么 |
|---|---|---|
| `status.cmd` | 查看本地状态与计划任务 | 不调用模型，不争租约 |
| `status.cmd -Live` | 追加只读额度查询和执行配置校验 | 不代替 runner 消费槽位、刷新其持久额度状态或解除退避 |

所以重置卡之后做一次 Live 查询，即使看到额度已恢复，也不等于后台 runner 已经执行了恢复处理。

### 12.4 看日志时应如何理解

| 日志事件 | 含义 |
|---|---|
| `QUOTA_SNAPSHOT_CHANGED` | 一般额度快照发生变化，不代表一定重置或调用 |
| `QUOTA_RECOVERED_EARLY` | 旧到期点尚未到达时观察到用量下降或真实到期时间改变；原因未知 |
| `WINDOW_RESET_OBSERVED` | 观察到旧到期点已过且返回时间后移；只用于审计，不能据此证明手动使用了重置卡 |
| `ANCHOR_SKIPPED` | 本轮未通过触发判断，查看具体原因；某个 schedule 跳过不等于其他触发器也被永久关闭 |
| `ANCHOR_EXECUTED` | 工具执行了锚定且后续额度读取成功；不保证一定显示为精确的新 5h／7d 周期 |
| `ANCHOR_ABORTED` | 某阶段终止或失败；是否真正发起过调用要看 phase、次数与执行信息 |
| `ANCHOR_ALARM_SET` / `ANCHOR_ALARM_CLEARED` | 后台到期检查任务被设置／清除，不是声音通知 |
| `BACKOFF_SKIP` / `GLOBAL_BACKOFF_SKIP` | 正处于本机／集群退避，未正常执行额度读取流程 |

新提前恢复事件的 `quotaChange` 保存窗口类型、前后已用比例和前后到期时间，
写入运行日志、历史记录、待同步记录以及每日汇总计数。

**已回放的实际例子：2026-09-14 至 09-15**

- 09-14 21:56：secondary 已用 90%，到期 09-19 16:22:10。
- 09-14 22:56：secondary 已用 10%，到期 09-21 22:06:48。修复版回放产生提前恢复记录。
- 09-15 08:56：primary 0%，到期 13:56:49；09:00:08 读到 0%，到期后移为 14:00:04。
- 修复版回放在 09:00:08 允许 schedule；回放没有发起真实模型调用，也没有改写原历史日志。
