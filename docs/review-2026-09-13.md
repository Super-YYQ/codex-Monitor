# 项目审查（2026-09-13）

> 范围：`codex/production-readiness` 分支 `cecc808`。通读 `codex-quota-keeper/scripts/` 全部模块、README、`docs/*.md`、CI 工作流；文中行号以该提交为准。
> 性质：审查建议，不是已决定的变更。哪些是从代码里确认的事实、哪些是需要真实数据验证的假设，正文分开标注。

## 结论摘要

1. **AutoAnchor 触发模型是最值得重做的部分。** 现在的 reset 触发不区分 5h/7d，keepalive 每 5 小时漂移触发、不看是否在用，两种模式互斥导致"7d 到期补枪 + 上班时间对齐 5h"做不到。建议改成两个独立开关：`schedule` 管 5h 对齐，`anchorOnExpiry` 管 7d 补空档；删除 keepalive 和 idle 判定。日均模型调用从最多 6 次降到 1–2 次，每次都有明确目的。
2. **到期时刻是提前已知的，应该用闹钟而不是轮询去追。** 读到 `resetsAt` 后注册一个一次性计划任务在 `resetsAt + 1 min` 拉起 runner；runner 现场重读额度再决定要不要打。闹钟不携带决策，过期或多余的闹钟只多花一次只读查询。
3. **先用真实数据回答一个问题**：7d/5h 窗口过期且没人使用时，`account/rateLimits/read` 返回的 `resetsAt` 是否前进。仓库里所有验证都是 mock，这个问题决定 reset 类触发是否有存在意义。
4. 多机租约/全局退避/Claim 这一层（约 1,400 行 + 测试）保护的是"重复锚定一次 = 多一条最小 prompt"，成本收益不成比例；服务端状态本身就是协调器。可以放到 v1.0 之后再决定是否砍。
5. 一批可以直接修的缺陷：定时槽位无迟到上限（B1）、本地网络错误写全集群退避（B5）、`dns|tls` 无词边界（B8）、`$readFailed` 死代码（B4）、forced runner 争锁失败静默丢弃（B7）。

## 1. AutoAnchor 触发模型

### 1.1 现状（代码确认）

| 触发器 | 位置 | 行为 |
|---|---|---|
| reset | `state-machine.ps1:228-247` | `prev.resetsAt < now` 且 `cur.resetsAt > prev.resetsAt` → `WINDOW_RESET_OBSERVED`。**primary（5h）和 secondary（7d）一视同仁**，都会触发锚定 |
| idle | `state-machine.ps1:418-436` | 从未锚定 + 第二次观测 + primary `usedPercent = 0` → 打一枪。存在的原因是给 reset 检测提供"基线" |
| keepalive | `state-machine.ps1:437-455` | 距上次锚定 ≥ 300 分钟 → 打一枪。槽位按 `floor(epoch / 5h)` 对齐（`:139-146`），**不检查 usedPercent**，活跃使用中照打 |
| schedule | `state-machine.ps1:359-369` | 当天所有"已过时刻且未处理"的槽位都算 due。**配置任意槽位即关闭以上三种触发**（互斥） |
| pending 队列 | `runner.ps1:207-214` + `state-machine.ps1:376-384` | 被静默期拒绝的 reset 事件保留到下一轮重试 |

### 1.2 为什么 5h 的 reset / keepalive 价值很低

- 锚定的收益 = 窗口过期到下一次真实使用之间的空档长度。5h 窗口在工作日内的空档只有午休级别；夜间/周末空档虽长，但凌晨 4 点锚出的 4:00–9:00 窗口本来就用不到。7d 窗口的空档动辄一两天，收益才可观。
- "上班时间卡好"是对齐边界，不是填空档，这正是定时模式的活：08:55 打一枪 → 08:55–13:55、13:55–18:55 两个整窗口覆盖工作日。keepalive 按 epoch 槽位漂移，永远对不齐作息。
- pending 队列 + 300 分钟静默期的组合会让一个被拒的 reset 事件在两小时后"补打"，补打时窗口早被用户自己开了。

### 1.3 reset 触发的根本疑问（假设，需真实数据验证）

`WINDOW_RESET_OBSERVED` 只在 `cur.resetsAt > prev.resetsAt` 时产生。服务端在窗口过期且空闲时的行为只有三种可能：

| 服务端语义 | 过期空闲时 `resetsAt` | reset 触发的价值 |
|---|---|---|
| A. 第一条消息才开新窗口 | 不变 / 变空 | **零**：`resetsAt` 前进恰恰说明用户自己已经开了新窗口，再补一枪是浪费 |
| B. 到点自动滚动 | 自动前进 | **零**：窗口边界固定，锚定这件事本身无意义 |
| C. 读取时给出"预计"的下一个 `resetsAt`，但窗口未真正开始 | 前进 | 有价值：是"窗口空闲可锚"的信号 |

仓库里所有测试和 soak 都是 mock；`docs/soak-runbook.md:174-180` 也说明 `normal` mock 下三种触发都打不着。**建议从真实 `history/` 里找 `WINDOW_RESET_OBSERVED` 事件，对照当时是否有人在用 Codex**，先确定是 A/B/C 哪一种，再决定 reset 类触发的去留。

### 1.4 建议：两个独立开关，各管一个窗口

| 开关 | 管什么 | 触发条件 | 不设置时 |
|---|---|---|---|
| `schedule: ["08:55"]` | 5h 窗口对齐作息 | 到点拉起 runner（Task Scheduler 原生 `-Daily -At`）；runner 重读额度，5h 窗口已在运行则跳过 | keeper 不碰 5h，靠用户自己使用开窗 |
| `anchorOnExpiry: ["secondary"]` | 7d 窗口不留空档 | **窗口不在运行**（`resetsAt` 为空或 ≤ now）且这次到期还没补过 → 打一枪 | keeper 不碰 7d |

- 两个开关**可同时启用**，去掉互斥。
- 想恢复"24 小时连续锚 5h"，把 `"primary"` 也加进 `anchorOnExpiry`；配合 1.5 的一次性任务，是严丝合缝的 5h 接 5h，不像 keepalive 那样每轮漂 0–59 分钟。
- 保留一个总闸 `autoAnchor.enabled`（默认 false）：两个触发器配了但总闸没开也不调模型。调模型是有条款解释风险的那一步，值得多一道显式确认。
- **两个开关都不设 = 纯查询**，只读额度、写日志、（多机时）维护租约，永不执行 `codex exec`，等价于现在的 `mode: MonitorOnly`。
- 删除 keepalive（被 `anchorOnExpiry: ["primary"]` 覆盖且更准）和 idle 判定（触发条件改成看当前快照后，不再需要"基线"）。
- 去重键：`hash(bucket | window | 最后一次非空 resetsAt | expired)`，一次到期只补一枪。多机场景 A 机补完，B 机下一轮读到窗口已在运行，自然不会再打。

### 1.5 轮询周期不变，到期用闹钟追

轮询周期仍是 `poll.intervalMinutes`（默认 60），触发器不决定轮询频率。两类到期分开处理：

- **可预知的到期**（7d 正常走完）：`resetsAt` 提前 7 天就知道。每次轮询读到后，把一个一次性计划任务指到 `resetsAt + 1 min`。到期后 1 分钟补枪，与轮询频率无关。
- **不可预知的重置**（服务端统一重置）：没有预告，只能靠轮询发现，延迟 = 轮询周期。想更快就把 `poll.intervalMinutes` 调到 15–30；`account/rateLimits/read` 是只读接口，不走模型、不耗额度。

**闹钟原则：计划任务只负责"到点把 runner 叫起来"，不负责"要不要打"。** 一次性任务拉起的是和整点轮询同一个 runner，走同一套流程：读额度 → 窗口是否在运行 → 不在运行才 `codex exec`。

一次性任务的维护规则只有一条：**每次轮询都把它重新指向"当前追踪的窗口里最早的 `resetsAt` + 1 分钟"**（同一个任务名，改触发时间，不新建）；没有窗口就删掉它。中途发生统一重置的例子：

| 时间 | 发生了什么 | runner 做了什么 |
|---|---|---|
| 周一 10:00 轮询 | 读到 7d `resetsAt` = 周六 03:00 | 一次性任务指到周六 03:01 |
| 周三 14:00 | 服务端统一重置，窗口被清空 | — |
| 周三 15:00 轮询 | 读到窗口不在运行 | 补一枪 → 新 `resetsAt` = 下周三 15:0x；一次性任务改指到下周三 15:01 |
| 周六 03:01 | 任务已被改走，什么都不发生 | — |

即使哪一步没改成功、周六 03:01 任务真的跑了：runner 读一次额度，看到窗口正在运行，记 `ANCHOR_SKIPPED`，退出。多花一次查询，不多花一次模型调用。

同一原则套到 `schedule`：08:55 触发器叫起 runner，runner 先读额度，5h 窗口已在跑（用户 08:30 就开始用了）也跳过。顺带解决 B1：槽位迟到超过一个轮询周期直接标记处理过、不执行。

实现细节：一次性任务可能和整点轮询撞在一起（03:00 轮询还在跑 git 同步，03:01 的任务来了）。现在的本地锁是抢不到就 `RUNNER_SKIPPED` 退出（`runner.ps1:61-67`），会让补枪推迟到下一轮。由一次性任务拉起的 runner 应等锁最多 60 秒再放弃（与 B7 同类问题）。

### 1.6 统一重置的覆盖

服务端统一重置在接口上只会是两种样子，新条件都能正确处理，现在的代码反而抓不到第二种：

| 重置形态 | 快照特征 | 该不该锚定 | 新条件 | 现在的代码 |
|---|---|---|---|---|
| 清用量、窗口照跑 | `usedPercent` → 0，`resetsAt` 不变或变成 now+7d | 不该：窗口在运行，打了也不改变边界 | 不触发 | 不触发（只记 snapshot changed） |
| 整个窗口清掉，下一条消息重开 | `resetsAt` 变空 / 回到过去 / 窗口从返回里消失 | **该**：越早补，下一次重置越早 | `resetsAt` 为空或 ≤ now → 下一轮触发 | **不触发**：`state-machine.ps1:232` 要求 `prev.resetsAt < now`，窗口中途被清时 prev 还在未来；窗口消失走 `WINDOW_DISAPPEARED`（`:264-268` 明确"never infer a reset from a vanished window"） |

新条件只看当前快照里窗口是否在运行，不依赖上一轮怎么变，正常到期、中途清空、窗口消失一个判断全覆盖。

### 1.7 wakeToRun 与收益边界

keeper 全靠计划任务到点拉起；任务以 `LogonType Interactive` 运行（`install.ps1:124`），`task.wakeToRun` 默认 false（`install.ps1:120`）。7d 到期补枪的收益完全取决于到期那一刻电脑能不能跑任务：

| `wakeToRun` | 到期时刻电脑睡眠 | 结果 |
|---|---|---|
| false（默认） | 任务不跑，等下次电脑醒着时补跑（`StartWhenAvailable`，`:116`） | 周一开机坐下才补枪，那时用户本来就要用 Codex，**补枪等于没补** |
| true | Windows 从睡眠/休眠唤醒，跑 runner，按电源策略再睡回去 | 准时开窗，下次重置提前到 7 天后同一时刻 |

限制：只能从睡眠/休眠唤醒，**关机唤不醒**；笔记本合盖放包里被唤醒会发热，笔记本建议保持 false，接受"下次开机再补"。桌面机建议开 true。

## 2. 产品定位

- **真正的卖点是 AutoAnchor，却被标成"实验、默认关、有风控风险"**；MonitorOnly 的产出只有 JSONL + `status.cmd` 文本，没有消费者（无图、无通知、无阈值告警）。Codex CLI 自带 `/status`，"每小时记一次额度"对个人用户价值很薄。二选一：要么承认这是**额度窗口调度器**、监控是配套；要么把监控做出出口（7d 用量超阈值 toast、周报页、重置时间提醒）。
- **多机互斥保护的是只读查询，这个操作几乎免费**；真正需要去重的是锚定，而重复锚定一次的代价是一条 `Reply exactly OK.`。lease CAS + 全局退避 + claim 状态机 + 仓库绑定（约 1,400 行 + 对应测试）保护一个价值近零的 at-most-once，是项目最大的复杂度来源。
- Windows-only（Task Scheduler + wscript + PS 5.1 兼容）。Codex CLI 用户大头在 macOS/Linux，不打算跨平台的话 README 第一行就该说清。

## 3. 架构

1. **服务端状态本身就是协调器。** 所有机器读到的 rateLimits 是同一份账号状态；触发条件写成"过期且未重启"后，A 机锚定，B 机下一轮自然看到窗口已开、不会再打——多机安全由触发条件的幂等性免费获得。60 分钟轮询下两机秒级撞车概率可忽略，撞上的代价是一条最小 prompt。coordination 可以降级成可选的 history 同步，租约/退避/claim 整层可删。这是大决定，可放到 v1.0 之后，但值得认真权衡。
2. 每个 tick 最多 3 轮 fetch+push（选举 `runner.ps1:122`、续租 `:305`、同步 `:322`）。配置校验已强制 TTL ≥ 2×poll，poll 后的续租是冗余的，可省一半 Git 流量。
3. **一台机器的 NETWORK_ERROR/TIMEOUT 会写全集群退避 10 分钟**（`runner.ps1:179-181`）。本地断网不是服务端信号，不该让别的机器停；且 pending marker 在网络恢复后才送达，那时已无意义。全局退避应只对 429/auth。
4. 两层开关表达一件事：`mode=AutoAnchor` + `codex.autoAnchor.enabled`（`common.ps1:380` 注释自己承认"mode alone is not enough"）；`leader.enabled` + `github.coordination.enabled` 需要 README 一张 4 行矩阵来解释。各合成一个。
5. 配置面 30+ 键，还有 TTL/poll/grace 关系约束。个人工具建议给 preset：`single-pc`、`single-pc+weekly-anchor`、`multi-pc`。

## 5. 安全

做得对的：不碰 `auth.json`、参数数组不走 shell、日志仓库绑定 + 业务分支黑名单、白名单字段投影、秘钥扫描不排除 `tests/`。补充：

- **S1** 部署目录若是 `D:\Tools\...` 这类非用户私有路径，`runtime\hidden-launch.vbs` 和 `scripts` 对同机其他用户可写 → 在当前用户会话里执行任意代码。README 建议路径改为 `%LOCALAPPDATA%`，或 install 时检查目录 ACL 并告警。
- **S2** `Hide-SensitiveText` 是关键字启发式；错误文本里的完整路径（含 Windows 用户名）不脱敏。READ_FAILED 不进 history，但 AUTH_ERROR 会。多机同步到私仓风险低，既然做了白名单不妨把路径也归一化。
- **S3** prompt 禁 `%$"` 等元字符是因为 `.cmd` 走 cmd.exe；根本解法是 npm 安装时直接调 `node <codex.js>` 而不是 `codex.cmd`，限制可以去掉，Unicode prompt 也更安全。
- **S4** `status.cmd -Live` 在 PASSIVE 机器上也直接查询额度（`status.ps1:126`），和"任意时刻只有 Leader 查询"的承诺不一致——手动操作可接受，文档应说明。

## 6. 功能优化

1. 精确调度（1.5）——对 AutoAnchor 效果影响最大。
2. 通知：runner 里加 Windows toast（7d 用量超阈值 / 锚定执行 / AUTH_ERROR），零常驻也能做。
3. 报表：从 history JSONL 生成一页本地 HTML（用量曲线、重置时间、锚定记录），给监控数据一个出口。
4. status 增加"下一次预计重置""下一次计划锚定"两行。
5. `schedule` 支持星期（`"Mon 08:55"`）。
6. 仓库整理：根目录 `findings.md / progress.md / task_plan.md` 是会话工作文件，与 `docs/` 同名文件重复，公开仓库首页不该有；README 255 行太长，拆出 20 行 quick start。

## 7. 建议顺序

1. 用真实 history 验证 1.3 的假设——决定 reset 触发是否有存在意义。
2. 触发模型重构（1.4）：primary→schedule、secondary→anchorOnExpiry、去互斥、删 keepalive/idle。B1–B3、B6 一起消掉。
3. Task Scheduler 原生精确触发 + 闹钟原则（1.5）。
4. 修 B5/B8/B4/B7 这类小错。
5. 再考虑是否砍 Git 租约层（架构 1）。
